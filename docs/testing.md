# Тестування FairFare

## Стратегія

Шар доступу до даних (DAL) перевіряємо інтеграційними тестами на справжньому PostgreSQL 16:
xUnit піднімає контейнер через Testcontainers і застосовує ті самі міграції, що й застосунок.
In-memory провайдер EF Core і SQLite не підходять, бо обмеження CHECK, зовнішні ключі (`NO ACTION`),
унікальні індекси і `ILIKE` працюють у них інакше, ніж у PostgreSQL.
Кожен тест працює зі своїми `Guid`, тому тести ізольовані й не залежать від порядку виконання.

Бізнес-правила шару BLL (наприклад, правила для учасників) перевіряємо швидкими модульними
тестами без бази даних.

Запуск: `cd src && dotnet test FairFare.Tests` (для інтеграційних тестів потрібен запущений Docker).

## Що покрито

| Група | Приклади |
| --- | --- |
| Основні сценарії | збереження і завантаження події з учасниками, додавання учасника, видалення події з усіма дочірніми записами, пошук за назвою без урахування регістру, сума витрат |
| Оновлення графа | видалення учасника, якого немає у новому графі; повторне збереження не дублює записи; видалення учасника зі списку завантаженої події |
| Крайові ситуації БД | дубль порядку зупинки, видалення учасника з витратами, порожня назва, дубль імені без урахування регістру, сума <= 0, від'ємна частка |
| Крайові ситуації DAL | подія без витрат, пошук без збігів, видалення неіснуючої події |
| Модульні тести BLL | додавання і видалення учасника, заборона дублів і порожніх імен, заборона видалення платника і боржника, заборона змін у завершеній подорожі |

## Приклади рефакторингу

1. `DeleteAsync`: події з витратами видаляються явно (частки, витрати, подія) в одній транзакції,
   бо платник і боржник мають `ON DELETE NO ACTION`, і каскад від учасників був би небезпечним.
2. `SaveAsync`: оновлення графа з ідентифікаторами, створеними на клієнті, виконується через `TrackGraph`
   (нові записи додаються, наявні оновлюються), а записи, що зникли з графа, видаляються окремо.
3. `EventService`: перевірка «подорож активна» винесена в один приватний метод `EnsureActive`,
   який використовують додавання і видалення учасника.
4. Запланований рефакторинг: перенесення `IEventRepository` у BLL і асинхронні команди в UI.
